# ЛР №3 — вход и права доступа

## Роли

| Роль | Права |
|---|---|
| `SUPERVISOR` | Управляет учётными записями, каталогом и всеми приёмами |
| `ADMIN` | Читает справочник пользователей, управляет каталогом, назначениями процедур врачам и всеми приёмами |
| `RECEPTIONIST` | Читает справочник, создаёт, просматривает, переносит и отменяет приёмы |
| `DOCTOR` | Читает и завершает свои приёмы, редактирует выполненные процедуры на своих приёмах, смотрит собственные свободные окна |
| `PATIENT` | Записывается от своего имени, просматривает, переносит и отменяет свои приёмы, смотрит свободные окна врачей |

Каталог процедур доступен на чтение всем вошедшим пользователям. При прокрутке приёмов условие по идентификатору пациента или врача применяется в PostgreSQL до ограничения размера страницы. Курсор строится по времени создания и UUID последнего приёма в выборке.

## Вход и запуск

Скопируйте `.env.example` в `.env`. Укажите случайный `JWT_SECRET` длиной от 32 байт, отдельный случайный `INTERNAL_API_TOKEN` и пароль первого супервайзера длиной от 12 символов и до 72 байт UTF-8. Для локального запуска подойдёт вывод `openssl rand -hex 32` для каждого из трёх значений. На существующей БД сохраните действующие настройки подключения PostgreSQL.

```bash
docker compose up --build
```

Откройте [Swagger](http://localhost:8080/swagger-ui.html) и выберите **catalog**. Отправьте `POST /api/v1/auth/login` с `email` и `password` из настроек супервайзера. Нажмите **Authorize** и вставьте значение `accessToken`. Swagger добавит префикс `Bearer`. В curl и других клиентах передавайте заголовок `Authorization: Bearer <accessToken>`.

Проверки для демонстрации:

1. Вызовите `GET /api/v1/auth/me`. Ответ содержит UUID, email и роль.
2. Создайте пациента через `POST /api/v1/users` с JWT супервайзера.

   ```json
   {
     "fullName": "Иван Иванов",
     "phone": "+79990000010",
     "email": "ivan@example.com",
     "password": "ExamplePatientPass123!",
     "role": "PATIENT"
   }
   ```

3. Войдите как пациент и повторите создание пользователя. Ожидаемый статус — `403`. Запрос к защищённому маршруту без JWT или с недействительным JWT вернёт `401`.
4. Создайте врача с ролью `DOCTOR`, специализацией из Swagger и рабочими часами. Выберите документ **appointments**. С JWT пациента создайте приём с его UUID в `patientId`, UUID врача в `doctorId` и временем внутри рабочего дня. Попытка записать другого пациента вернёт `403`.
5. Войдите как врач. В `GET /api/v1/appointments` будут его приёмы. Врач может выполнить `PATCH /api/v1/appointments/{id}/complete` для своего приёма.

## Пароли и перенос данных

Пароль хранится как BCrypt-хеш с коэффициентом 12. Пароль принимают только вход, создание пользователя и смена пароля. Публичные ответы и внутренние DTO каталога его не содержат.

Liquibase сохраняет существующие UUID и переводит роль `DIRECTOR` в `SUPERVISOR`. При запуске каталог создаёт супервайзера по настроенному email или задаёт начальный пароль активному супервайзеру с этим email, если хеш отсутствует. Если email уже занят другой ролью, настройте свободный адрес или адрес существующего супервайзера. После первого запуска можно очистить **обе** переменные `BOOTSTRAP_SUPERVISOR_EMAIL` и `BOOTSTRAP_SUPERVISOR_PASSWORD`.

Для пользователя из ЛР №2, у которого ещё нет пароля, супервайзер вызывает `PUT /api/v1/users/{id}/password` с JSON `{"password":"..."}`. Операция также заменяет существующий пароль.

## JWT и внутренние вызовы

Каталог выдаёт JWT с подписью HS256, идентификатором пользователя, ролью и сроком действия. Gateway и оба бизнес-сервиса проверяют подпись, издателя и срок действия. JWT хранит роль на момент входа. Уже выданный токен действует до истечения срока даже после смены пароля, роли или деактивации. Срок настраивается через `JWT_TTL_SECONDS`, по умолчанию 900 секунд.

Feign передаёт `X-Internal-Token` для вызова внутренних методов каталога. Маршруты `/internal/**` закрыты на Gateway и скрыты в публичном Swagger.
